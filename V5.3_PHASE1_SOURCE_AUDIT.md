## 3. Critical gaps confirmed by source inspection

### 3.1 Writes still held only in React state

`src/context/AppContext.tsx` currently changes local state for important operations rather than waiting for a server-confirmed write. Confirmed examples include:
- `generateInvoice()` — adds invoice with `setInvoices()`.
- `submitResidentPayment()` — adds receipt with `setReceipts()` and changes invoice state locally.
- `confirmAndAllocatePayment()` — updates receipts, bill allocations, invoices and bank balances locally.
- `addExpense()` and `approveExpense()` — update expenses and bank balances locally.
- `createActivityRequest()` / `updateActivityRequest()` — update request state locally.
- `createNotice()` — updates notice state locally.

These are not safe as the authoritative society ledger until server APIs persist and validate them.

### 3.2 Backend write API coverage is limited

The current `doPost()` routes login, password reset, logout, selected user/KYC actions, profile update and `submitPayment`. The requested full CRUD endpoints for properties, owners, ownership, rates, invoices, payment confirmation/allocation, expenses, notices, activity requests, etc. are not present in `Code.gs`.

The existing `submitPayment_()` appends a row but does not currently provide the full requested controls: server-generated receipt number under lock, idempotency key, comprehensive amount/ownership validation, payment proof upload, audit trail and confirmation/allocation transaction.

### 3.3 All-at-once data loading

`doGet()` handles `getSocietyData` by opening the society spreadsheet and reading every configured sheet. `AppContext.tsx` calls this endpoint on load and populates all major collections. This contradicts the requested module-by-module selective loading and can increase latency and response size.

### 3.4 Session token appears in URL

`AppContext.tsx` calls:

`GET ?action=getSocietyData&token=<session token>`

Tokens in URLs can appear in browser/network history, logs or diagnostics. Protected read operations should move to POST body requests using the existing Apps Script-compatible request pattern, then be tested in a real browser.

### 3.5 Central Master lookup reads whole tabs

`societyAndUsers_()` calls `sheetObjects_()` for the complete Society Master and Society User Access tabs. `requireSession_()` invokes this lookup for each protected request. It does re-check account state and role, which is useful for revocation, but the repeated full-sheet reads are a performance concern.

### 3.6 Hardcoded configuration

`Code.gs` contains Central Master Spreadsheet ID and default Drive Folder ID constants. `authClient.ts` and `AppContext.tsx` contain a hardcoded Apps Script Web App URL. These should be moved to controlled deployment configuration and excluded from public source where appropriate. The Apps Script deployment URL is not itself a password, but configuration should not be duplicated.

### 3.7 Hardcoded bank payment details in UI

`src/components/payments/PaymentsView.tsx` contains literal bank name, account number, IFSC and UPI values. These should be loaded from the society's configured payment instructions, with sensitive bank account master data still protected by role permissions. Confirm the displayed values with the society owner before any live use.

### 3.8 Role and ownership enforcement incomplete

The current backend has role checks on user-administration actions. The generic data-read path filters Resident records by property for several sheets, but every future write/read endpoint still needs explicit server-side permission and ownership checks. Frontend menu hiding is not sufficient.

### 3.9 Drive upload scope incomplete

Only KYC upload is implemented. The requested owner/property documents, payment proofs, invoice PDFs, vouchers, gallery, request and notice attachments are not implemented as a complete permission-checked upload/download workflow.

### 3.10 Audit and financial atomicity incomplete

The current audit helper is limited and suppresses errors. Payment confirmation/allocation and expense approval are not implemented as server-side locked, idempotent financial transactions. Client-side balance adjustments must not be treated as accounting truth.

## 4. Configuration and build observations

- `vite.config.ts` uses `base: '/abas-sathi/'`; the GitHub repository/project Pages path must match or the base must be changed.
- `.github/workflows/deploy.yml` uses Node.js 22 and `npm install`, then `npm run build`.
- `package.json` defines `dev`, `build`, `preview`, `clean`, and `lint`; `lint` is `tsc --noEmit`, not ESLint.
- There is no `test` script despite `src/utils/calculations.test.ts` being present.
- The archive does not include a lockfile, so installs are not fully reproducible. Add and commit a package lock after dependency installation.
- `npm install --no-audit --no-fund` did not finish within the available 120-second execution window; therefore TypeScript checks, tests and production build were not run. No build/test success is claimed.

## 5. Database mapping items to reconcile before implementation

- Backend config uses the sheet name `Invoice_Register` (underscore), while user-facing roadmap wording has also used `Invoice Register` (space). The live spreadsheet's exact tab name and headers must be confirmed before migration; do not rename or reorder live data automatically.
- `SOCIETY_SHEETS` includes 21 tabs. The source's migration notes document the canonical Property Master area fields: `Carpet_Area`, `Allocated_Common_Area`, `Structural_Area`, `Super_Built-up_Area`.
- Central Master uses `Society Master` and `Society User Access`; society databases include `User Master & Role Management`. These are distinct tables and must not be conflated.
- Multi-society folder mapping must use the authenticated society record's Drive Folder ID; the current KYC implementation uses one global `DEFAULT_DRIVE_FOLDER_ID` plus a society-named subfolder.

## 6. Phase 1 conclusion

**Version 5.2 is a functioning UI with authenticated login, authenticated bulk reads and selected user/KYC/payment-submission backend actions. It is not yet a complete production accounting application.**

Do not use local React state as the permanent ledger, and do not use this version as the sole live financial record until server-side financial writes, authorization, idempotency, audit, Drive permissions, backup/restore and end-to-end tests are complete.

## 7. Recommended implementation sequence

1. Confirm exact live sheet/tab names and headers; produce a read-only mapping report.
2. Define one API response/error contract and central frontend API client.
3. Implement paginated, selective read endpoints and dashboard summary.
4. Implement generic validation and role/property/society authorization helpers.
5. Implement master-data CRUD (Property, Owner, Ownership, Rate, categories, accounts, etc.).
6. Implement invoice generation, payment submission/confirmation/allocation and expense approval as locked, idempotent server-side transactions.
7. Implement activity requests, notices, gallery and maintenance workflows.
8. Implement private Drive upload/download with file metadata and recovery states.
9. Add audit, backup/restore and operational logging.
10. Add automated tests and run browser tests against the owner's deployed Apps Script and test spreadsheet.

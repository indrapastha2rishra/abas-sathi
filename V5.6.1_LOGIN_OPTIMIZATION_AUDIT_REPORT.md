# ABAS SATHI Version 5.6.1 — Login Optimization Audit & Release Notes

**Base source:** ABAS SATHI 5.5.3 (uploaded ZIP)  
**New release:** 5.6.1  
**Scope:** targeted login-path optimization and privacy-safe performance instrumentation. Existing schema and business logic preserved.

## Audit Findings (source-confirmed)

1. Login calls a single `login` Apps Script action; the 5.5.3 frontend already avoids an immediate redundant `getMyProfile` request.
2. Backend `loginContext_()` opens the Central Master spreadsheet, reads Society Master headers and searches the Society Code, then searches Login_ID in Society User Access and reads matching candidate rows.
3. The login-only lookup called `ensureHeaders_()` on Society User Access, which can perform a header write on the authentication path even though authentication only needs to read existing columns.
4. Password verification uses the configured 12,000-iteration HMAC-SHA256 derivation. This intentionally expensive work is security-sensitive and was not reduced.
5. Successful login writes `Last_Login`; legacy SHA-256 credentials are upgraded to the current KDF on successful sign-in.
6. The authenticated application provider starts dashboard bootstrap after login. The dashboard path uses `getDashboardData`, which reads many role-specific sheets in one backend execution. This is a significant post-authentication workload and can affect when populated dashboard widgets appear.
7. The client login request has a 20-second timeout and does not automatically retry the login request. A duplicate-submit ref lock is already present.

## 5.6.1 Changes made

### Frontend
- Added privacy-safe timing diagnostics to successful login: frontend total time and backend authentication/lookup/password-verification timings. No society/login identifiers, password, token or response object is logged.
- Preserved local validation, duplicate-submit guard, loading state, no-password-storage policy and single login request.

### Apps Script backend
- Removed `ensureHeaders_()` from the login-only lookup path. Header repair is setup/administrative maintenance, not an authentication operation.
- Authentication now validates that required login columns exist, without mutating sheet structure on login.
- On successful login, reads the user-access header once and resolves the relevant column indexes once, reducing redundant header reads when updating Last_Login and migrating a legacy password.
- Added successful-authentication timing fields to the response: lookupMs, passwordVerifyMs, authMs. These are operational timings only and contain no authentication secrets.
- Password KDF rounds, account-status validation, society matching, rate limiting, constant-time hash comparisons, legacy migration, token generation and session TTL are unchanged.

### Versioning
- `package.json` version set to 5.6.1.
- `metadata.json` description updated to 5.6.1.
- README version references updated to 5.6.1.

## Limitations / remaining work

- The existing bulk dashboard bootstrap has **not** been replaced with a complete server-aggregated, progressive dashboard architecture in this patch. It still loads many dashboard datasets. That is a likely remaining post-login bottleneck and needs a separate carefully tested refactor to preserve calculations.
- The 3-second login-to-dashboard target cannot be guaranteed on Google Apps Script/Sheets. Cold starts, network latency, spreadsheet access and 12,000-round password derivation remain external/intentional latency contributors.
- No live society credentials, central master spreadsheet, deployed Apps Script environment or production mobile browser were available for end-to-end timing.
- Login measurements are instrumented; real measurements must be collected after deployment and should be compared on a warm and cold backend.

# ABAS SATHI Version 5.5.3 — Performance Remediation Report (বাংলা)

## 1. Source audit: পাওয়া Root Causes

### Login
- আগের Login path-এ Central Master-এর Society User Access tab থেকে একটি Society-র সব user row download করে `Login_ID` খোঁজা হতো। User সংখ্যা বাড়লে login lookup-ও ধীর হতো।
- Password যাচাইয়ে 12,000-round HMAC-SHA256 KDF আছে। এটি নিরাপত্তার অংশ; এই release-এ iteration কমানো হয়নি।
- Returning session restore-এ `getMyProfile` backend round-trip হয়। এটি নতুন Login-এর অংশ নয়, তবে browser reload-এর পর app shell দেখানোর আগে অপেক্ষা করায়।

### Upload / data submission
- `uploadPrivateFile_()` Drive folder lookup, Drive file creation, sharing permission, registry write, related-record update এবং audit write—সবকিছু একটি global `ScriptLock` ধরে করছিল। একই Apps Script project-এর অন্য Society-র write-ও ওই lock-এর জন্য অপেক্ষা করতে পারত।
- `createPrivateSocietyFolder_()` প্রতিটি upload-এ Central Master-এর Society এবং user access rows পুনরায় lookup করছিল।
- Property ও Owner validation-এর জন্য সম্পূর্ণ sheet object read করে `.some()` করা হচ্ছিল, যদিও ID lookup দরকার ছিল।
- Browser FileReader দিয়ে Data URL তৈরি করে পরে Base64 substring নেওয়া হচ্ছিল; এতে অপ্রয়োজনীয় intermediate string তৈরি হচ্ছিল।
- Upload failure-এর পর `STARTED` operation আটকে থাকত; একই requestId-এ retry করলে retry অসম্ভব হতো।

### Dashboard / retrieval
- Dashboard module plan-এ Audit Log-ও চাওয়া হচ্ছিল, যদিও dashboard view-তে সেটি দেখানো হয় না।
- Financial Dashboard-এর invoice, receipt, bill allocation এবং expense history এখনো সম্পূর্ণ পড়তে হয়, কারণ বর্তমান UI-তে এগুলি browser-এ totals, trend, outstanding ও fund calculations-এর জন্য ব্যবহৃত হয়। Financial correctness না বদলে এই history truncate করা হয়নি।

## 2. এই source release-এ করা পরিবর্তন

1. **Targeted Login lookup:** নতুন `loginContext_()` Society_Code এবং Login_ID কলামে `TextFinder` ব্যবহার করে matching row-গুলি পড়ে। পুরো Society User Access table browser/server memory-তে আর আনা হয় না। Password KDF, role validation, account status validation ও session token rules অপরিবর্তিত।
2. **Operation ledger lookup:** `findOperation_()` সম্পূর্ণ `_Operation Ledger` download না করে Operation_ID-এর matching row খোঁজে।
3. **Drive folder cache:** `createPrivateSocietyFolder_()` society-specific private folder ID Script Cache-এ 6 ঘণ্টা রাখে; cache miss/invalid ID হলে Central Master থেকে resolve করে এবং folder privacy পুনরায় যাচাই করে।
4. **Short lock sections:** Upload-এর global ScriptLock শুধু idempotency reservation এবং registry/link commit-এর সময় নেওয়া হয়। Drive folder resolution ও `folder.createFile()` lock-এর বাইরে চলে। অন্য user-এর upload/write-কে Drive upload শেষ হওয়া পর্যন্ত অপেক্ষা করতে হয় না।
5. **Upload validation:** PropertyID/OwnerID যাচাইয়ে সম্পূর্ণ sheet read বাদ দিয়ে `rowById_()` ব্যবহার করা হয়। Related record থেকে PropertyID/OwnerID পাওয়া গেলে File Registry-তে শুরু থেকেই final values লেখা হয়; পরে দ্বিতীয় scan/update লাগে না।
6. **Upload recovery:** Upload operation `FAILED` হলে একই requestId-এ retry করা যায়। Commit ব্যর্থ হলে best-effort rollback-এ registry row সরানো, related document reference restore এবং Drive file trash করা হয়।
7. **Generic data submission:** `createRecord_()`-এর cross-sheet validation lock নেওয়ার আগে করা হয়; uniqueness ও ownership-share constraints-এ critical revalidation lock-এর ভিতরে থাকে। Append-only Audit Log event lock section-এর বাইরে `appendRow()` দিয়ে লেখা হয়।
8. **Browser file conversion:** File Data URL intermediate বাদ দিয়ে `File.arrayBuffer()` থেকে Base64 তৈরি হয়। File size/type limit একই—5 MB, PDF/JPG/PNG।
9. **Upload timeout:** 5 MB পর্যন্ত upload-এর জন্য client timeout 60 seconds; normal API request 25 seconds। Upload-এ blind automatic retry বন্ধ রাখা হয়েছে; একই requestId user retry-তে পুনর্ব্যবহৃত হয়।
10. **Dashboard bootstrap:** Dashboard module plan থেকে অপ্রয়োজনীয় Audit Log request বাদ। Financial historical rows অক্ষত।

## 3. Data integrity ও permission

- 21টি business sheet-এর নাম/columns পরিবর্তন করা হয়নি।
- Invoice, Receipt, Bill Wise Details, Expense, Journal, Voucher এবং Year-End Closing calculations truncate বা alter করা হয়নি।
- Server-side `requireSession_()`, `requireRole_()`, Resident property checks, document category permissions, private Drive checks এবং idempotency checks রাখা হয়েছে।
- Upload size/type/category rules অপরিবর্তিত।
- নতুন কোনো database migration বা sheet column প্রয়োজন নেই। Script Cache folder reference স্বয়ংক্রিয়ভাবে তৈরি হবে।

## 5. Deployment procedure

1. Backup GitHub repository, Central Master spreadsheet and each Society database spreadsheet.
2. Replace the GitHub repository source with this complete ZIP contents. Keep the current configured Central Master ID, default Drive folder ID and deployed Web App URL in Apps Script Script Properties / browser settings as appropriate; do not publish private IDs or credentials.
3. In Apps Script, replace `Code.gs` with `apps_script/Code.gs`, save, then deploy a **new Web App version** (Execute as Me; access Anyone, as required by this frontend).
4. Confirm the frontend is configured with the current `/exec` URL.
5. On a development machine with network access, run `npm install`, `npm test`, `npm run lint`, and `npm run build`. Resolve all errors before deploy.
6. Deploy frontend to a staging URL first. Use test users for Admin, Committee, Accountant and Resident.
7. Test owner document, payment proof, gallery photo and notice attachment uploads; verify File Registry row, linked record reference, Drive privacy and access restrictions.
8. Test simultaneous uploads from two different societies and one financial write during an upload. Verify no duplicate file, no missing registry entry, no incorrect society association and no lock timeout.
9. Compare Dashboard totals, outstanding, FY receipts/payments, and year-end closing against source Sheets. Only then promote staging to production.

## 6. Known remaining architecture limits

- Apps Script + Sheets is not a high-throughput database. Financial sheets still grow over time and some report/dashboard paths scan full history to preserve exact accounting totals.
- The 12,000-round password KDF intentionally remains; login timing still depends on Apps Script runtime and the KDF. A large performance improvement here requires migration to Firebase Authentication or another managed password-auth service, not weakening the current hash.
- Upload transport still sends Base64 through Apps Script, so a large file on a slow mobile connection remains network-bound. A future direct-to-Cloud-Storage signed upload flow would be faster but requires a different backend and security architecture.
- Global ScriptLock remains in financial write transactions and short critical create-record sections to protect double-entry and idempotent ledger updates. This patch removes the long Drive operation from that lock, but does not remove serialization from financial posting.

**Release status:** complete source package with targeted performance fixes and passing static/regression checks; **staging candidate, not live-production-certified** until the live tests in section 5 pass.
